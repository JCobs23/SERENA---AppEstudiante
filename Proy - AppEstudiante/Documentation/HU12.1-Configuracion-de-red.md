# H.U.12.1 – Configuración de red del aula

## Objetivo

Permitir que la aplicación del estudiante configure en un único lugar la dirección base del servidor utilizado por las pantallas de ingreso, registro, sala de espera y narrativa. La aplicación conserva la clave existente de `PlayerPrefs`, `SerenaServerUrl`, y no cambia rutas ni contratos HTTP.

## Arquitectura de conexión del cliente

`SerenaServerConfig` centraliza la lectura, validación, normalización y persistencia de la URL. Los controladores `SessionCodeEntryController`, `StudentNameController`, `StudentReadyButtonController`, `StudentRosterController`, `NarrativeStartListener` y `NarrativeStageView` consultan `SerenaServerConfig.BaseUrl` antes de construir sus solicitudes.

La interfaz de configuración está en la escena de ingreso (`1_IngresoCodigo`), implementada por `SessionCodeEntryController`. El botón **Servidor** abre el panel; **Guardar** valida y persiste la dirección; **Cerrar** vuelve al ingreso. La configuración se conserva entre ejecuciones mediante `PlayerPrefs`. La URL debe ser absoluta y usar HTTP, acorde con el protocolo identificado en el cliente. Si no incluye puerto, se conserva sin añadir uno y se muestra un aviso para especificarlo cuando el despliegue lo requiera.

El valor inicial de compatibilidad sigue siendo `http://192.168.1.18:5080`. Es un valor serializado que ya existía en el proyecto; no se afirma que sea la dirección real del servidor del aula.

## Protocolo y puerto identificados

- Protocolo observado: HTTP.
- Métodos observados: GET y POST; los POST existentes envían sus payloads actuales.
- Puerto en el valor inicial y las URL serializadas inspeccionadas: `5080`.
- No se identificó uso de WebSocket.

El puerto 5080 describe la configuración existente del cliente, no confirma el puerto definitivo de despliegue. La modificación no altera endpoints, métodos, payloads ni respuestas esperadas.

## Configurar la URL en una tablet

1. Abrir la aplicación y permanecer en la pantalla de ingreso del código.
2. Pulsar **Servidor**.
3. Escribir la dirección base accesible del servidor. Para la entrada móvil se puede pulsar **Abrir teclado**.
4. Incluir el puerto si el servidor del aula lo requiere. La aplicación no agrega un puerto automáticamente.
5. Pulsar **Guardar** y verificar el mensaje de confirmación; si la URL no incluye puerto, revisar el aviso mostrado.
6. Cerrar el panel e ingresar un código de sesión para comprobar la conectividad.

No introducir rutas `/api/...` en el campo: se espera la dirección base del servidor. No introducir credenciales ni contraseñas.

## Requisitos de red que deben confirmarse

La tablet y el servidor deben poder comunicarse por la red del aula. El servidor debe escuchar en una interfaz alcanzable desde la LAN, y el firewall del equipo servidor debe permitir el tráfico TCP al puerto que se confirme para el despliegue. El router o punto de acceso debe permitir la comunicación entre clientes Wi-Fi y el equipo servidor; una opción de aislamiento de clientes puede impedirla.

Estos son requisitos que se deben verificar en la instalación; el proyecto no confirma la configuración del router, firewall ni interfaz de escucha del servidor.

## Prueba manual con una tablet

1. Confirmar con el responsable del aula la dirección IP o nombre del servidor y el puerto habilitado.
2. Conectar tablet y servidor a la red autorizada.
3. Configurar la URL desde **Servidor** y comprobar que queda guardada cerrando y abriendo la aplicación.
4. Ingresar un código de sesión conocido y verificar la respuesta de la pantalla.
5. Si falla, revisar dirección, puerto, conectividad LAN, firewall y escucha del backend; no concluir que una URL responde solo porque pasó la validación de formato.

La validación de formato es local. No se añadió una solicitud de prueba de servidor ni se realizaron pruebas físicas.

## Prueba manual con varias tablets

1. Configurar la misma URL confirmada en cada tablet.
2. Conectar todas a la red del aula y comprobar individualmente que ingresan a una sesión válida.
3. Ejecutar el flujo de estudiantes previsto por el equipo y confirmar que el servidor recibe las solicitudes de cada dispositivo.
4. Observar latencia, errores de conexión y restricciones del punto de acceso con el número de tablets esperado.

La concurrencia real depende del servidor y de la red del aula; no se ha probado con varios dispositivos.

## Datos pendientes de confirmar en el aula

- IP o nombre definitivo del servidor.
- Router/punto de acceso y si permite comunicación entre clientes.
- Reglas de firewall aplicables.
- Interfaz de red en la que escucha el backend.
- Puerto definitivo expuesto por el backend.
- Conectividad real desde una y varias tablets.
- Capacidad del servidor y de la red para la concurrencia prevista.
